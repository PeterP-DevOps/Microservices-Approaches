# Домашнее задание к занятию «Микросервисы: подходы» - Петр Петров

### Задача 1: Обеспечить разработку

Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:

- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;- 
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.
Обоснуйте свой выбор.

### Решение 1:

Можно организовать через GitLab.com — это и хранилище кода, и CI/CD в облаке. Каждый микросервис — в своём Git‑репозитории. В каждом репозитории лежит файл .gitlab-ci.yml — там описан пайплайн. Он стартует сам, когда что‑то пушим в Git, но можно и вручную запустить, если надо изменить параметры.

Чтобы везде было одинаково, берём общие CI/CD‑шаблоны — так процессы не будут разбегаться. Секреты (типа токенов и паролей) кидаем либо в защищённые переменные CI/CD, либо во внешний secret manager.

Сборку запускаем на GitLab Runner’ах в Docker‑контейнерах. Если задача специфичная, можно подключить self‑managed runners — то есть свои раннеры на инфраструктуре компании. Образы Docker храним прямо в GitLab Container Registry.

Параллельность делаем за счёт нескольких раннеров  — так тесты и сборки не встают в очередь, а идут кучей.

Такое решение позволяет построить единый управляемый процесс CI/CD, сохранить воспроизводимость сборок и масштабировать инфраструктуру по мере роста количества микросервисов.  

### Задача 2: Логи

Предложите решение для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре. Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:

- сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
- минимальные требования к приложениям, сбор логов из stdout;
- гарантированная доставка логов до центрального хранилища;
- обеспечение поиска и фильтрации по записям логов;
- обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
- возможность дать ссылку на сохранённый поиск по записям логов.
Обоснуйте свой выбор.

### Решение 2:

В качестве системы централизованного сбора и анализа логов можно использовать стек ELK: Elasticsearch, Logstash и Kibana, дополненный Filebeat в качестве агента сбора логов. Микросервисы не требуют специальной интеграции с системой логирования и записывают логи в stdout/stderr. На каждом хосте разворачивается Filebeat, который собирает логи контейнеров и передаёт их в Logstash. Logstash выполняет обработку, фильтрацию и преобразование записей и передаёт их в центральный кластер Elasticsearch. Elasticsearch используется для распределённого хранения и быстрого поиска логов. Kibana предоставляет веб-интерфейс для поиска, фильтрации и анализа логов, а также позволяет предоставить разработчикам доступ с использованием ролей и сохранять результаты поиска. Для повышения отказоустойчивости Elasticsearch разворачивается в виде кластера из нескольких узлов, а Filebeat и Logstash используют механизмы повторной передачи и буферизации. Данное решение обеспечивает централизованный сбор логов со всех хостов, поиск и фильтрацию записей, разграничение доступа и возможность передачи сохранённых поисковых запросов разработчикам.

### Задача 3: Мониторинг

Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре. Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:

- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.
Обоснуйте свой выбор.

### Решение 3:

В качестве системы мониторинга можно  использовать связку Prometheus + Node Exporter + cAdvisor + Grafana. Prometheus используется для централизованного сбора и хранения временных рядов метрик, а также для выполнения запросов и агрегации данных с помощью PromQL. На каждом хосте устанавливается Node Exporter, который предоставляет метрики CPU, RAM, дисковой подсистемы и сети. Для контроля потребления ресурсов отдельными Docker-контейнерами используется cAdvisor, предоставляющий метрики CPU, RAM, Network и файловой системы контейнеров. Для получения специфических метрик микросервисов приложения должны предоставлять endpoint /metrics в формате Prometheus, содержащий, например, количество запросов, ошибки, задержки и бизнес-метрики. Grafana используется как пользовательский интерфейс для выполнения запросов к Prometheus и построения настраиваемых dashboard. Для разных уровней мониторинга создаются отдельные панели: состояние хостов, состояние контейнеров, производительность микросервисов и специфические бизнес-метрики. Такое решение обеспечивает централизованный сбор метрик всей инфраструктуры, возможность детального анализа состояния ресурсов и создание единого визуального интерфейса мониторинга.
